Core E-Commerce Checkout con Descuentos Acumulativos

Documento de diseño de software para la prueba técnica "Core E-Commerce con Sistema de Descuentos Acumulativos". Cubre historias de usuario ejecutables, arquitectura y patrones de diseño, motor de descuentos, modelo de datos, contrato de API, seguridad/IAM, mensajería y saga, resiliencia, despliegue en GCP/Kubernetes, y estrategia de pruebas — con el nivel de detalle necesario para que un desarrollador implemente sin ambigüedad tanto el backend como el frontend.

Frontend React + TypeScript + Shadcn/ui + SCSS Backend NestJS + TypeScript + Prisma + PostgreSQL Infra GCP · GKE · Supabase (DB + Auth) · Redis · SSE
01

Resumen y alcance

Cómo se concilia el MVP de 20 minutos exigido por la prueba con el stack "enterprise" solicitado, sin sacrificar ninguno de los dos.

El enunciado pide un MVP demostrable en una sustentación de 20 minutos. El brief de arquitectura solicitado añade, además, un conjunto de piezas propias de un sistema en producción a escala (Kubernetes, mensajería asíncrona, Saga, Event Sourcing, IAM, cifrado de payloads, Redis como pool de conexión). Construir literalmente todo eso como código funcional dentro del tiempo de la prueba es poco realista y, peor, iría en contra del criterio explícito de evaluación: "evalúa el criterio de ingeniería del desarrollador sobre la cantidad de código".

D
Decisión de arquitectura: este SDD se organiza en dos niveles explícitos. El Nivel MVP es el que se codifica, se prueba con cobertura ≥80% y se demuestra en vivo. El Nivel Enterprise es la arquitectura objetivo a la que ese MVP evoluciona sin reescrituras — documentada, con contratos e interfaces ya preparados en el código del MVP, pero cuya infraestructura pesada (K8s, IAM completo) no se levanta para la demo. Esto es exactamente lo que docs/arquitectura.md pide justificar como trade-off de "simplicidad vs. extensibilidad".

Stack fijado

Frontend: React + TypeScript + Shadcn/ui + SCSS. Backend: NestJS + TypeScript + Prisma + PostgreSQL (Supabase). Esta decisión ya no se trata como una opción entre varias (el enunciado permitía elegir libremente) — queda cerrada para todo el resto del documento.

Descomposición en microservicios

El backend no es un monolito modular: cada dominio es un servicio NestJS independiente — su propio main.ts, su propio puerto, su propio Dockerfile, desplegable por separado. Un API Gateway es el único punto público; el resto solo se habla entre sí por red interna (docker-compose en local, ClusterIP dentro de GKE en producción).

!
Esto invalida un supuesto de la primera versión de este SDD: con módulos dentro de un mismo proceso, el checkout completo cabía en una sola transacción SQL y "no había nada distribuido que orquestar". Con servicios separados eso deja de ser cierto — reservar stock, resolver el cupón y calcular el descuento son ahora llamadas de red independientes, y un paso puede fallar después de que otro ya tuvo efecto. La saga de §09 se reescribe sobre esta base: deja de ser "documentada para el futuro" y pasa a ser parte del MVP.

Durante el diseño se revisaron cuatro piezas de la lista inicial de requisitos y se reemplazaron por una alternativa más coherente con seis microservicios pequeños compartiendo una sola instancia de base de datos gestionada (§01 "Descomposición en microservicios"). Esta tabla es, literalmente, el contenido que va en la sección de trade-offs de docs/arquitectura.md.

02

Historias de usuario — plan de implementación

Cada HU del enunciado, descompuesta en tareas concretas de backend y frontend, en el orden en que un desarrollador ("coder") debe ejecutarlas.

i
Orden de construcción recomendado: HU3 (motor + API) antes que HU1/HU2 (UI), porque el frontend consume el contrato que define el backend. Implementar el motor de descuentos primero, con sus pruebas unitarias, congela el contrato CheckoutResponseDto que todo lo demás depende.

HU 3 · Procesamiento consistente de la orden

Backend

Como API REST, recibo el carrito y el cupón, valido stock, recalculo el motor de descuentos con precedencias y tope del 35%, decremento stock, persisto la orden y devuelvo los totales desglosados.

Tareas
  1. Inicializar apps/backend/services/ con seis proyectos NestJS independientes (api-gateway, catalog-service, coupon-service, discount-service, order-service, notification-service), TypeScript estricto en todos ("strict": true, sin any implícito).
  2. En catalog-service, coupon-service y order-service: cada uno con su propio prisma/schema.prisma apuntando a su propio schema de Postgres dentro de la misma instancia de Supabase (ver §06) y corriendo prisma migrate dev --name init por separado.
  3. Sembrar productos y cupones de prueba con prisma db seed en catalog-service y coupon-service (ver §06 "Semilla de datos") para tener catálogo real desde el primer arranque.
  4. En discount-service, crear src/strategies/discount-strategy.interface.ts con el contrato DiscountStrategy (ver §04). Este servicio no tiene base de datos.
  5. Implementar las 3 estrategias concretas: CategoryDiscountStrategy, VolumeDiscountStrategy, CouponDiscountStrategy, cada una en su propio archivo bajo src/strategies/ de discount-service.
  6. Implementar DiscountStrategyFactory.buildPipeline() en src/factories/discount-strategy.factory.ts: devuelve el arreglo ordenado de estrategias (orden fijo = orden de precedencia del negocio).
  7. Implementar DiscountEngineService.calculate(): recorre el pipeline, acumula resultados, aplica el tope del 35% al final (método applyAbsoluteCap, puro y testeable en aislamiento). Exponer como POST /internal/discounts/calculate.
  8. Escribir primero las pruebas unitarias del motor (ver §12) antes de conectar cualquier controlador — el motor no debe depender de Nest, Prisma ni HTTP en absoluto.
  9. En catalog-service, implementar StockService.reserveStock(items): valida stock >= quantity por producto dentro de una transacción Prisma, lanza InsufficientStockException (HTTP 409) si falla cualquier línea. Exponer POST /internal/stock/reserve y POST /internal/stock/release (compensación, ver §09).
  10. En order-service, implementar OrdersRepository — único punto que conoce Prisma en ese servicio; OrdersService nunca importa el cliente Prisma directamente (aislamiento persistencia/lógica, ver §03).
  11. En order-service, implementar CheckoutSaga.run(dto): llama a catalog-service (reservar), coupon-service (resolver), discount-service (calcular), persiste orden + items + fila outbox en su propia transacción, y compensa (libera stock) si la persistencia falla (ver §09).
  12. En api-gateway, exponer POST /api/v1/checkout que reenvía a order-service, con CreateCheckoutDto validado por class-validator (rechaza carritos vacíos o con quantity <= 0 con 400).
  13. Decorar los controladores con @ApiTags/@ApiResponse de @nestjs/swagger en cada servicio; api-gateway agrega los esquemas en /api/docs (ver §07).

HU 1 · Gestión del carrito

Frontend

Como cliente, veo el catálogo (id, nombre, precio, categoría, stock) y agrego/quito productos del carrito con el subtotal actualizándose de inmediato.

Tareas
  1. Inicializar apps/frontend con Vite + React + TypeScript estricto.
  2. Instalar Shadcn/ui (npx shadcn@latest init) y generar los componentes base: button, card, badge, input, separator, toast/sonner, alert-dialog.
  3. Configurar SCSS junto a Tailwind (el motor de utilidades de Shadcn): carpeta src/styles/ con _tokens.scss (colores/espaciados propios de marca) y módulos *.module.scss para componentes con layout propio (carrito, desglose, alerta) — Tailwind resuelve utilidades atómicas, SCSS resuelve composición visual específica del dominio. Documentar este híbrido como decisión en docs/arquitectura.md.
  4. Crear el store del carrito en src/state/cart.store.ts con Zustand (patrón Observer: cada componente se suscribe solo a la porción de estado que necesita).
  5. Definir el tipo Product y CartLine en packages/shared-contracts (o src/types si no se usa el paquete compartido) — mismos campos que el DTO del backend, sin duplicar significados.
  6. Implementar ProductList + ProductCard (Shadcn Card) mostrando id, nombre, precio, categoría (badge) y stock restante; botón "Agregar" deshabilitado si stock === 0.
  7. Implementar CartPanel/CartItemRow con controles +/− por línea; el subtotal se deriva de un selector memoizado selectSubtotal(state), nunca de un cálculo disperso en el JSX.
  8. Cablear la API de productos: src/api/products.api.ts con fetch tipado hacia GET /api/v1/products.

HU 2 · Cupón y desglose de descuentos

Frontend

Como cliente, ingreso un cupón, presiono "Aplicar" y veo el desglose (categoría, volumen, cupón), el % efectivo, el ahorro total y el valor final.

Tareas
  1. Exponer POST /api/v1/checkout/preview en api-gateway, que llama directo a coupon-service (resolver) y discount-service (calcular) — sin pasar por order-service, porque no hay nada que persistir ni stock que reservar (idempotente, seguro de llamar en cada tecleo). Cero duplicación de reglas de negocio: es el mismo discount-service que usa HU3.
  2. Frontend: CouponForm con Input + botón "Aplicar" (Shadcn); al enviar, llama useCheckoutPreview() (hook en src/state/useCheckoutPreview.ts) que hace debounce de 300ms y dispara la petición de preview con el carrito actual + código.
  3. Implementar DiscountBreakdown.tsx mostrando cada línea (Categoría, Volumen, Cupón) con su monto, más "Ahorro total", "% de descuento efectivo" y "Total a pagar" — estilo propio en DiscountBreakdown.module.scss.
  4. Si el cupón no existe, está vencido o aún no es vigente, el preview responde coupon:{applied:false, reason:'INVALID_COUPON'|'EXPIRED_COUPON'|'NOT_YET_VALID'} (no es un error HTTP, es un resultado de negocio) — el formulario muestra el motivo sin bloquear el resto del cálculo.
  5. Al confirmar la compra, reusar el mismo payload contra POST /api/v1/checkout (HU3) para persistir.

HU 4 · Alerta de descuento límite alcanzado

Frontend

Si la combinación de productos y cupón supera el 35%, veo una notificación persistente y distintiva.

i
Hallazgo de ingeniería a defender en sustentación: con exactamente las 3 reglas obligatorias del enunciado (10% × 5% × 15% en cascada), el descuento combinado máximo matemáticamente posible es 1 − (0.90 × 0.95 × 0.85) = 27.325%, sin importar la composición del carrito — el tope del 35% nunca se activa con solo WELCOME2026. Pero en cuanto HU7 permite cupones de categoría con porcentaje configurable (ej. TECH30), el tope sí se vuelve alcanzable con datos legítimos — ver el ejemplo 2 de §04. El guard se prueba en aislamiento (inyectando resultados sintéticos al método applyAbsoluteCap) precisamente para no depender de armar a mano el carrito exacto que lo dispare. Ver §04 y §12.
Tareas
  1. El backend siempre retorna cappedAt35: boolean en la respuesta del preview/checkout, calculado por applyAbsoluteCap.
  2. Frontend: componente DiscountCapAlert.tsx — banner persistente (no un toast que desaparece) usando Shadcn Alert variante destructiva/warning + estilo distintivo propio en SCSS (fondo con textura de "borde de precaución" o franja de color acentuado), texto exacto: "¡Enhorabuena! Has alcanzado el límite máximo de ahorro permitido (35%)."
  3. El banner se muestra/oculta reactivamente según breakdown.cappedAt35 proveniente del preview — no hay estado local duplicado.
  4. Prueba de render: dado un breakdown mockeado con cappedAt35: true, el banner debe estar presente en el DOM con el texto exacto (edge case explícito del enunciado, ver §12).
i
HU 5, 6 y 7 son adicionales — van más allá del mínimo exigido por el enunciado (que solo pide HU1–HU4). Se incluyen porque el equipo pidió explícitamente login, checkout de invitado, administración de inventario y gestión de cupones. Presentarlas como "valor agregado" en la sustentación, dejando claro que HU1–HU4 son las que la rúbrica evalúa de forma obligatoria.

HU 5 · Autenticación y datos de entrega Adicional

Backend

Como cliente, quiero poder iniciar sesión para comprar; si no tengo cuenta, quiero que se me pidan mis datos de entrega antes de confirmar la compra.

Tareas — Backend
  1. Habilitar Supabase Auth en el proyecto (email/password); no se implementa un endpoint propio de login — el frontend habla directo con Supabase (ver §08).
  2. Middleware/guard SupabaseAuthGuard en common/guards/supabase-auth.guard.ts: si llega Authorization: Bearer, verifica la firma contra el JWKS de Supabase y adjunta req.user; si no llega, deja pasar la request como invitado (no la rechaza) — es un guard opcional, distinto de uno que exige sesión.
  3. Extender CheckoutRequestDto con guestInfo?: { fullName, email, phone, address } (ver §07).
  4. En OrdersService.checkout(): si req.user existe, usar user.id; si no, validar que guestInfo venga completo (400 si falta un campo) y cifrarlo con JWE antes de guardarlo en orders.guest_info_enc (ver §08 — este es el uso concreto de JWE en el proyecto).
  5. Endpoint PATCH /api/v1/users/me/profile (Customer) para que un usuario logueado guarde una dirección de entrega por defecto y no tenga que reescribirla en cada compra.
Tareas — Frontend
  1. LoginForm/RegisterForm (Shadcn Form + Input) usando el SDK cliente @supabase/supabase-js (signInWithPassword, signUp).
  2. authStore.ts (Zustand, patrón Observer) guarda la sesión de Supabase y expone isAuthenticated/roles al resto de la app.
  3. En el checkout: si authStore.user es null, mostrar botón "Continuar como invitado" que revela GuestCheckoutForm.tsx (nombre, email, teléfono, dirección) — todos obligatorios para habilitar "Confirmar compra".
  4. Si hay sesión activa, precargar los campos de entrega desde el perfil guardado, editable antes de confirmar.

HU 6 · Administración de inventario Adicional

Backend

Como administrador, quiero crear productos manualmente y ajustar su stock, para gestionar el catálogo sin tocar la base de datos directamente.

Tareas — Backend
  1. RolesGuard(['ADMIN']) se verifica en api-gateway (lee req.user.roles resuelto por SupabaseAuthGuard) antes de reenviar la request a catalog-service.
  2. En catalog-service: POST /admin/products — crea producto (sku, nombre, precio, categoría, stock inicial), validado con class-validator. El gateway lo expone como POST /api/v1/products.
  3. PATCH /admin/products/:id — edita nombre/precio/categoría (no toca stock).
  4. PATCH /admin/products/:id/stock — ajuste atómico { delta: number } con UPDATE products SET stock = stock + $delta WHERE id = $id AND stock + $delta >= 0, para no pisar una compra concurrente (mismo cuidado que reserveStock, que vive en este mismo servicio).
  5. DELETE /admin/products/:id — soft delete (active = false): nunca borrar físicamente un producto ya referenciado por order_items históricos en order-service.
Tareas — Frontend
  1. Ruta protegida /admin/inventario: si authStore.roles no incluye ADMIN, redirige a inicio.
  2. ProductsTable.tsx (Shadcn Table/DataTable) con ajuste de stock inline (+/−) que llama al endpoint de stock.
  3. ProductFormDialog.tsx (Shadcn Dialog + Form) para crear/editar producto, con Select de categoría.

HU 7 · Catálogo y administración de cupones Adicional

Backend

Como administrador, quiero crear cupones nuevos, globales o por categoría (ej. Tecnología, Juguetería). Como cliente, quiero ver los cupones disponibles y aplicarlos con un clic, sin tener que adivinar el código.

D
Extensión del motor de descuentos: WELCOME2026 sigue siendo obligatorio y fijo (15%, alcance global). Los cupones que cree el administrador añaden un segundo tipo: alcance por categoría (ej. TECH30 → 30% solo en líneas de Tecnología, JUGUETES10 → 10% solo en Juguetería). Ver §04 "Actualización: cupones por categoría" para el cambio de diseño que esto exige en CouponDiscountStrategy — y para un ejemplo donde, con un cupón así, el tope del 35% sí se activa con datos reales.
Tareas — Backend
  1. En coupon-service, extender el modelo Coupon: scope: 'GLOBAL' | 'CATEGORY', categoryId? (referencia liviana, sin FK entre schemas, a la categoría que vive en catalog-service), label.
  2. GET /available (pública vía gateway como /api/v1/coupons/available) — solo cupones active=true y vigentes, exponiendo únicamente code, label, scope, categoryName, discountPercent. Nunca listar cupones inactivos/expirados.
  3. POST /admin/coupons y PATCH /admin/coupons/:id (ADMIN, vía gateway).
  4. coupon-service expone POST /internal/coupons/resolve; order-service lo llama y pasa el resultado a discount-service, que ramifica CouponDiscountStrategy.apply() según scope (detalle en §04).
Tareas — Frontend
  1. AvailableCouponsPanel.tsx en el checkout: tarjetas/chips por cupón público (ej. "WELCOME2026 · 15% en toda la compra", "TECH30 · 30% en Tecnología"), botón "Usar" que rellena CouponForm y dispara el preview automáticamente.
  2. Ruta /admin/cupones (Shadcn DataTable + Dialog) para crear/editar cupones, con Select de categoría cuando scope = CATEGORY.
03

Arquitectura y patrones de diseño

Vista de componentes de extremo a extremo y los patrones exigidos por el enunciado, con su ubicación exacta en el código.

Aislamiento del motor de descuentos

DiscountEngineService y sus estrategias viven en el servicio discount-service, que ni siquiera tiene conexión a base de datos — su único propósito es recibir un DiscountContext plano por HTTP interno y devolver un CheckoutBreakdown plano. Ninguna otra parte del sistema reimplementa la cascada: order-service lo invoca, nunca al revés. Esto responde directamente la pregunta obligatoria de docs/arquitectura.md de forma aún más estricta que en un monolito — el aislamiento no es solo de carpeta, es de proceso.

Patrones de diseño implementados (mínimo 2, aquí van 5)

04

Motor de descuentos acumulativos

Algoritmo exacto, en cascada multiplicativa, con el tope absoluto del 35%.

Fórmulas

subtotal_categoria = Σ (precio_i × cant_i × 0.90 si categoria_i = "Tecnologia", sino × 1.00) subtotal_volumen = subtotal_categoria × 0.95 si subtotal_categoria > 100, sino subtotal_categoria subtotal_cupon = subtotal_volumen × 0.85 si cupon activo y vigente, sino subtotal_volumen descuento_bruto = subtotal_original − subtotal_cupon tope_absoluto = subtotal_original × 0.35 descuento_final = min(descuento_bruto, tope_absoluto) total_final = subtotal_original − descuento_final pct_efectivo = descuento_final / subtotal_original (0 si subtotal_original = 0)
!
Aritmética monetaria: nunca operar montos en number flotante sin control. Trabajar en centavos enteros (Math.round(valor * 100)) o con una librería decimal (decimal.js) para evitar errores de redondeo acumulados en la cascada — de lo contrario dos ejecuciones del mismo carrito pueden diferir en un centavo y romper una prueba de "igualdad exacta".

  category: string;
  originalAmount: number;

export interface DiscountContext {
  readonly originalSubtotal: number;
  readonly lines: ReadonlyArray<CartLineState>;
  readonly runningSubtotal: number;      // = suma de remainingAmount, mantenido en sync
  readonly resolvedCoupon?: {
    scope: 'GLOBAL' | 'CATEGORY';
    categoryName?: string;
    discountPercent: number;
  };
}

// CouponDiscountStrategy.apply() — resumen
function apply(ctx: DiscountContext): DiscountResult {
  const pct = ctx.resolvedCoupon!.discountPercent / 100;
  const targets = ctx.resolvedCoupon!.scope === 'CATEGORY'
    ? ctx.lines.filter(l => l.category === ctx.resolvedCoupon!.categoryName)
    : ctx.lines;
  const amount = targets.reduce((sum, l) => sum + l.remainingAmount * pct, 0);
  // devuelve DiscountResult + nuevas lines con remainingAmount actualizado solo en `targets`
}

Vigencia = dos fechas, no una. coupons.valid_from y coupons.valid_to ya estaban en el modelo de datos (§06), pero la primera versión de este documento nunca los comparaba explícitamente contra now en ningún lado — solo se mencionaba "cupón vigente" en prosa. coupon-service resuelve el código así, y es resolve() — no el motor de descuentos — quien decide la vigencia:
// coupon-service/src/coupons.service.ts — POST /internal/coupons/resolve
function resolveCoupon(code: string, now: Date): ResolvedCoupon | { applied: false; reason: DiscountReason } {
  const coupon = repository.findByCode(code);
  if (!coupon) return { applied: false, reason: 'INVALID_COUPON' };
  if (!coupon.active) return { applied: false, reason: 'INVALID_COUPON' };
  if (now < coupon.validFrom) return { applied: false, reason: 'NOT_YET_VALID' };
  if (now > coupon.validTo) return { applied: false, reason: 'EXPIRED_COUPON' };
  return { scope: coupon.scope, categoryName: coupon.categoryName, discountPercent: coupon.discountPercent };
}

Un schema de Postgres por servicio

Los 6 microservicios de §01/§03 comparten la misma instancia de Supabase (una sola factura, un solo backup) pero nunca la misma tabla: cada uno tiene su propio schema de Postgres y su propio DATABASE_URL (mismo host, search_path distinto). Tablas de auditoría con triggers, nombre ofuscado y firma HMAC

Se usa una única tabla central de auditoría con nombre no descriptivo (evita que una exploración casual del esquema revele su propósito) y un trigger genérico reutilizado en cada tabla sensible, en vez de una tabla de auditoría por entidad. Cada fila se firma con HMAC (extensión pgcrypto) sobre su propio contenido, para que una modificación posterior de la fila de auditoría — no solo del dato original — sea detectable:

-- migrations/002_audit_triggers.sql (Prisma migration escrita a mano)

CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE _x27f_evt_trace (
  id            BIGSERIAL PRIMARY KEY,
  entity_name   TEXT NOT NULL,          -- tabla origen (products, orders, coupons...)
  operation     TEXT NOT NULL,          -- INSERT | UPDATE | DELETE
  row_pk        TEXT NOT NULL,
  actor         TEXT,                   -- current_setting('app.current_user', true)
  old_data      JSONB,
  new_data      JSONB,
  occurred_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  hmac_signature TEXT NOT NULL          -- integridad: hmac(fila, clave de servidor)
);

-- Solo el rol ADMIN puede leerla directamente
REVOKE ALL ON _x27f_evt_trace FROM PUBLIC;
GRANT SELECT ON _x27f_evt_trace TO role_admin;

CREATE OR REPLACE FUNCTION _x27f_capture() RETURNS TRIGGER AS $$
DECLARE
  v_old JSONB := CASE WHEN TG_OP IN ('UPDATE','DELETE') THEN row_to_json(OLD) END;
  v_new JSONB := CASE WHEN TG_OP IN ('UPDATE','INSERT') THEN row_to_json(NEW) END;
BEGIN
  INSERT INTO _x27f_evt_trace(entity_name, operation, row_pk, actor, old_data, new_data, hmac_signature)
  VALUES (
    TG_TABLE_NAME,
    TG_OP,
    COALESCE(NEW.id::text, OLD.id::text),
    current_setting('app.current_user', true),
    v_old,
    v_new,
    encode(hmac(TG_TABLE_NAME || TG_OP || COALESCE(NEW.id::text, OLD.id::text) || COALESCE(v_new::text, v_old::text),
                current_setting('app.audit_hmac_key'), 'sha256'), 'hex')
  );
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER trg_products_audit AFTER INSERT OR UPDATE OR DELETE ON products
  FOR EACH ROW EXECUTE FUNCTION _x27f_capture();
CREATE TRIGGER trg_orders_audit AFTER INSERT OR UPDATE OR DELETE ON orders
  FOR EACH ROW EXECUTE FUNCTION _x27f_capture();
CREATE TRIGGER trg_coupons_audit AFTER INSERT OR UPDATE OR DELETE ON coupons
  FOR EACH ROW EXECUTE FUNCTION _x27f_capture();
!
La ofuscación del nombre no es seguridad real: es una capa adicional de defensa en profundidad (dificulta el reconocimiento visual al navegar el esquema). La protección real son dos cosas: Row-Level Security + GRANT restringido al rol role_admin (control de acceso), y la firma hmac_signature (detección de manipulación posterior). Explicar esta distinción en la sustentación evita que un evaluador la lea como "seguridad por oscuridad" mal entendida.

Seguridad, IAM y payloads cifrados

Supabase Auth para identidad de usuario, JWT firmado para sesión, JWE acotado a cifrar datos sensibles en reposo, roles IAM y service accounts para comunicación entre servicios.

Flujo de identidad

  1. El usuario se autentica directo desde el frontend contra Supabase Auth (@supabase/supabase-js, email/password) — no hay backend propio de login.
  2. Supabase devuelve un JWT firmado (JWS) con { sub, email, exp }; el frontend lo guarda en authStore y lo envía como Authorization: Bearer en cada request al backend.
  3. SupabaseAuthGuard (backend) verifica la firma contra el JWKS público de Supabase (sin llamar a un servicio externo por cada request — el JWKS se cachea), sin necesidad de un intercambio de token adicional.
  4. Los roles (CUSTOMER/ADMIN) se resuelven consultando la tabla local user_roles por supabase_uid (no van dentro del JWT de Supabase, que el backend no controla) y se adjuntan a req.user.roles.
  5. RolesGuard(['ADMIN']) reutiliza ese req.user.roles para proteger los endpoints de HU6/HU7.
i
Dónde queda JWE: el JWT de Supabase es solo firmado (JWS) — cualquiera puede leer su payload en base64, solo no puede alterarlo sin invalidar la firma; eso alcanza para autorización porque viaja por HTTPS y no lleva datos sensibles, solo sub/email/exp. El cifrado con JWE se reserva para un caso donde sí hay un dato sensible que proteger en reposo: el bloque guestInfo (nombre, email, teléfono, dirección) de un checkout sin cuenta (HU5), que se cifra antes de escribirse en orders.guest_info_enc y solo se descifra bajo demanda para ADMIN o para el propio flujo de despacho.
// guest-info.crypto.ts — cifrado con jose (A256GCM, clave simetrica en Secret Manager)
import { EncryptJWT, jwtDecrypt } from 'jose';

async function encryptGuestInfo(info: GuestInfoDto, key: Uint8Array): Promise<string> {
  return new EncryptJWT({ ...info })
    .setProtectedHeader({ alg: 'dir', enc: 'A256GCM' })
    .setIssuedAt()
    .encrypt(key);
}

async function decryptGuestInfo(blob: string, key: Uint8Array): Promise<GuestInfoDto> {
  const { payload } = await jwtDecrypt(blob, key);
  return payload as unknown as GuestInfoDto;
}

Autenticación servicio-a-servicio

Solo api-gateway verifica el JWT del usuario final. Los servicios internos (catalog-service, coupon-service, discount-service, order-service, notification-service) no vuelven a verificar ese JWT — confían en la red interna y exigen el header X-Internal-Token descrito en §07. Esto evita que cada servicio duplique la lógica de verificación de Supabase, a costa de que la red interna deba estar genuinamente cerrada (sin exposición pública de esos puertos) — trade-off explícito para docs/arquitectura.md. En el Nivel Enterprise ese token compartido se reemplaza por mTLS entre pods vía el service mesh de GKE, con la identidad de cada llamada dada por la ServiceAccount de Kubernetes del pod que llama (ver abajo), no por un secreto compartido.

Service accounts (nivel enterprise)

Cada worker de GKE corre bajo su propia Kubernetes ServiceAccount, vinculada vía Workload Identity a una service account de GCP IAM de mínimo privilegio: sa-order-service@PROJECT.iam.gserviceaccount.com (Cloud SQL Client + Secret Manager Accessor) y sa-inventory-worker@PROJECT.iam.gserviceaccount.com (mismo Cloud SQL, sin acceso a Secret Manager de la clave JWE de datos de invitado). Ningún pod usa una clave JSON de service account montada como archivo — Workload Identity evita ese secreto de larga vida. A nivel de Supabase, el backend usa la service_role key (privilegio total, salta RLS) solo desde el servidor; el frontend usa exclusivamente la anon key sujeta a RLS.

09

Eventos, patrón Saga y Outbox

Con 6 microservicios el checkout es genuinamente distribuido: la saga por orquestación deja de ser teórica.

D
Decisión de arquitectura: el checkout usa Saga por orquestación — order-service es el único orquestador, llama a los demás servicios en un orden fijo y es el único que sabe compensar. Se prefiere sobre coreografía para este tramo porque el flujo es lineal y de cuatro pasos: una cadena de eventos donde cada servicio reacciona al anterior sería más difícil de seguir para el mismo resultado. La Saga por coreografía (servicios reaccionando a eventos sin un orquestador central) se reserva para lo que pasa después de OrderConfirmed — notificación, y el día que exista una pasarela de pago externa como paso adicional.

La saga de checkout, paso a paso

Los tres primeros pasos (reservar, resolver cupón, calcular) son de solo lectura o reversibles sin efecto secundario si fallan antes de completarse — no necesitan compensación porque, si fallan, simplemente no dejaron nada que deshacer. El único paso con efecto persistente antes del commit final es la reserva de stock en catalog-service; por eso es el único con una compensación explícita (release).

Estados de la orden

Outbox transaccional (la base del "Event Sourcing" pedido)

En vez de mantener un event store completo desde el día uno, order-service implementa el patrón Transactional Outbox: cada cambio de estado relevante escribe una fila en su tabla outbox_events dentro de la misma transacción que el cambio de negocio (mismo schema order, ver §06). Un proceso OutboxRelay — dentro del propio order-service, no un servicio aparte — hace polling de filas status = 'PENDING' y las publica al canal Redis, marcándolas PUBLISHED. Esto da la garantía que Event Sourcing busca (ningún cambio de estado se pierde ni se publica sin haber ocurrido realmente) sin la complejidad operativa de reconstruir agregados desde un log de eventos completo.

Resiliencia

Pool de conexiones con Redis, circuit breakers y caminos explícitos de excepción en integraciones externas.

Redis como pool de conexión de la DB

El driver de Postgres (pg/Prisma) ya mantiene su propio pool TCP; lo que Redis añade aquí es un semáforo distribuido que limita cuántas consultas concurrentes puede emitir el conjunto de pods hacia la base de datos, algo que un pool local por proceso no puede coordinar entre réplicas durante un escalado automático agresivo en GKE.

!
Trade-off honesto para arquitectura.md: el estándar de la industria para pooling real de Postgres es PgBouncer (pooling a nivel de transacción, reduce conexiones reales en el servidor). El semáforo en Redis no reduce el número de conexiones abiertas; solo evita una tormenta de solicitudes simultáneas. Se documenta como complemento, no reemplazo — en una implementación de producción real se usarían ambos.
// redis-pool.provider.ts (semaforo tipo token-bucket)
async function withDbSlot<T>(redis: Redis, fn: () => Promise<T>): Promise<T> {
  const acquired = await redis.set('db:slots', '1', 'NX', 'EX', 5); // ejemplo simplificado
  // implementacion real: script Lua con contador + limite configurable (p.ej. 50 slots)
  try {
    return await fn();
  } finally {
    await redis.decr('db:active-connections');
  }
}

Circuit breaker

Con 6 servicios llamándose entre sí por red, un circuito abierto ya no es un caso raro de "integración externa" — es tráfico normal entre order-service y sus tres dependencias síncronas (catalog-service, coupon-service, discount-service). Cada llamada saliente (incluidas esas tres, más la verificación de JWT contra Supabase) se envuelve con opossum: tras N fallos consecutivos el circuito pasa a OPEN y responde con el fallback inmediatamente (sin seguir golpeando el servicio caído); tras un intervalo pasa a HALF_OPEN para probar con una sola solicitud antes de cerrar de nuevo.

Caminos de excepción por integración

IntegraciónFallaComportamiento
Supabase Auth (verificar JWT)JWKS inalcanzableCircuito abre en api-gateway → 503 "Servicio de autenticación no disponible" — la JWKS se cachea, así que solo afecta a tokens nuevos, no a sesiones ya validadas en esta instancia
order-service → catalog-service (reservar stock)Timeout / servicio caídoCircuito abre → checkout responde 503 con Retry-After; no se persiste nada (falla antes del primer efecto)
order-service → discount-service (calcular)Timeout / servicio caídoCircuito abre → compensación: se libera el stock ya reservado, checkout responde 503
Redis Pub/Sub (publish)Conexión rechazadaEl evento queda PENDING en el outbox; el checkout igual responde 201 al cliente (la publicación es eventual, no bloqueante); el relay reintenta con backoff exponencial
Base de datosPool agotadoExcepción tipada DbUnavailableException → 503 con Retry-After
Cupón / InventarioDato corrupto o inconsistenteSe trata como resultado de negocio (400 con detalle de validación), nunca como excepción no controlada 500

Pruebas y cobertura (80%)

Qué probar, cómo probar el edge case "imposible" del 35%, y cómo configurar el umbral como puerta de calidad.

Backend (Jest)

  • CategoryDiscountStrategy: aplica solo a líneas Tecnología; no aplica si no hay ninguna.
  • VolumeDiscountStrategy: umbral exacto en $100.00 (no aplica en 100.00, aplica en 100.01).
  • CouponDiscountStrategy / coupon-service.resolveCoupon: cupón inexistente, inactivo, expirado (now > valid_to) y aún no vigente (now < valid_from) — los cuatro casos retornan applied:false con su reason, sin lanzar excepción.
  • applyAbsoluteCap probado en aislamiento con un descuento bruto sintético del 50% → debe truncar a 35% exacto (así se cubre el edge case aunque sea inalcanzable con las 3 reglas reales).
  • Carrito vacío → subtotal 0, sin división por cero, effectiveDiscountPercentage = 0.
  • Payload corrupto (quantity: -1, productId inexistente) → 400 con detalle de validación.
  • InventoryService: solicitar más unidades que el stock disponible → InsufficientStockException, stock no se decrementa.

Frontend (Vitest + Testing Library)

  • cart.store: agregar/quitar líneas recalcula el subtotal derivado correctamente.
  • cart.store: no permite cantidad negativa ni superar el stock mostrado.
  • DiscountBreakdown: renderiza los 3 montos y el total final desde un breakdown mockeado.
  • DiscountCapAlert: visible con el texto exacto cuando cappedAt35 = true; ausente cuando es false.
  • CouponForm: muestra el motivo cuando el cupón es inválido/expirado sin bloquear el resto de la UI.
